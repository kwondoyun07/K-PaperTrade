## 소스 실측 결과

### 키움 REST API (현재 주력, 모의투자) — 2026-08-02 실측

`POST https://mockapi.kiwoom.com/api/dostk/chart`, 헤더 `api-id: ka10080`

- 토큰: `POST /oauth2/token {grant_type, appkey, secretkey}` → `{token, expires_dt}` (약 24시간)
- 바디: `{stk_cd, tic_scope: "1", upd_stkpc_tp: "1"}`
- 응답 배열 `stk_min_pole_chart_qry`, **최신순 900건/페이지**
  (`cntr_tm` YYYYMMDDHHMMSS, `open_pric`/`high_pric`/`low_pric`/`cur_prc`, `trde_qty` 분당 거래량)
- **가격에 +/- 부호가 붙어 온다** — 전일 대비 방향 표시일 뿐이므로 제거해야 한다
- 연속조회: 응답 헤더 `cont-yn=Y` + `next-key`를 다음 요청 헤더로.
  **한계 실측: 103페이지 92,492건, 2025-08-01까지 = 정확히 1년.**
  103페이지에서 `cont-yn=N`으로 자연 종료(005930 기준, 종목당 약 140초)
- **호출 제한: API ID당 초당 1회**(초과 시 HTTP 429 / 1700). 1.1초 간격 사용
- 실전 호스트(`api.kiwoom.com`)에 모의 키를 쓰면 8030으로 거부 — 실거래 오용이 자동 차단된다

공식 문서에서 확인한 추가 스펙(openapi.kiwoom.com):

- `tic_scope`: 1·3·5·10·15·30·45·60분 지원
- **`base_dt`(기준일자, YYYYMMDD) 파라미터가 있다** — 특정 시점을 앵커로 잡을 수 있어
  백필이 중단됐을 때 처음부터 다시 페이징하지 않고 재개할 수 있다
- 토큰 유효기간 **24시간**, 폐기는 `POST /oauth2/revoke {appkey, secretkey, token}`
- `pred_pre_sig`: 1 상한가 / 2 상승 / 3 보합 / 4 하한가 / 5 하락
- 응답 예제에 있는 `acc_trde_qty`(누적거래량)는 **스펙 표에 없는 미기재 필드**다. 실제로는 온다
- **모의투자는 대체거래소(NXT) 매매·계좌조회 미지원**(KRX만). 우리는 KRX만 쓰므로 무관
- **App Key/Secret은 발급 시 1회만 다운로드 가능** — 분실하면 재발급해야 한다
- **IP 화이트리스트: 계정당 최대 10개**. "허용된 IP에서만 API 인증이 가능"하다고만 적혀 있고,
  발급된 토큰으로 개별 TR을 호출할 때도 매번 IP를 검사하는지는 문서에 없다.
  → GitHub Actions(유동 IP)에서 동작하는지는 실측으로 판정한다(아래 운영 주의 참고)

**네이버와 대조(2026-07-31, 3종목 1,138봉): OHLC 전부 일치.**
시가·종가 단일가 봉의 거래량만 미세 차이(스냅샷 시점 차이로 추정).

교체 이유: 네이버는 ~6거래일뿐이라 "하루라도 놓치면 영구 유실"이었는데,
키움은 과거 백필이 가능해 그 위험이 사라진다. 공식 API이기도 하다.
실측: 1종목 6/1 이후 43거래일 16,213행 수집에 22초.

### 네이버 분봉 API (폴백, 비공식) — 2026-08-01 실측

`GET https://api.stock.naver.com/chart/domestic/item/{ticker}/minute`

- 파라미터: `periodSizeMinutes=1`, `startDateTime`/`endDateTime` (YYYYMMDDHHMM)
- 응답: JSON 배열 — `localDateTime`, `openPrice`, `highPrice`, `lowPrice`,
  `currentPrice`(종가), `accumulatedTradingVolume`
- **진짜 분봉 OHLC 제공** (구 fchart.stock.naver.com은 종가·누적량만 — 사용 안 함)
- `accumulatedTradingVolume`은 이름과 달리 **분당 거래량**
  (일합계가 일봉 거래량과 ±0.02% 일치 확인)
- 멀티데이 범위를 한 요청으로 조회 가능 (백필 = 종목당 1요청)
- **제공 범위: 최근 ~6거래일** → 일일 적재를 놓치면 그 날짜 분봉은 영구 유실.
  GitHub Actions cron이 생명선.
- 하루 381봉: 09:00~15:19 연속거래 + 15:30 종가단일가.
  급등일 등엔 장 초반 일부 분봉이 비는 경우 있음(시가단일가 지연 추정).

## 저장 전략

- **분봉 원본**: 일자별 parquet 1파일(전 종목 통합, zstd, `minute-YYYY-MM-DD.parquet`)
  → GitHub Release 자산(태그 `minute-YYYY-MM`). Turso에 넣지 않는 이유:
  일 105만 행 = 월 2,300만 행으로 무료 쓰기 한도(월 1,000만 행) 초과.
- **Turso krx_market**: 일봉·수급·지수(전 종목, 일 수천 행)와
  `minute_prices` 롤링 캐시(조회 종목 최근 5거래일)만.

## 일일 배치 흐름 (collector/daily.py, 평일 16:30 KST)

기준일은 **실행 시각 − 9시간의 날짜**다. 예약 실행이 밀려 자정을 넘기면 전일을 수집한다
(그냥 오늘 날짜를 쓰던 때는 다음 날을 "휴장"으로 판정하고 초록으로 끝났다 — 8/31 구멍의 원인).

1. 휴장 판정: 005930 분봉이 비면 지수 날짜로 묻는다(FDR → 네이버). 판정 불가는 실패.
2. Turso 적재(분봉보다 먼저): stocks upsert + 미등재 비활성화 → 코어 ETF 일봉
   → 수급(네이버, 실패 시 스킵) → 지수(FDR → 네이버) → 분봉 캐시 정리
3. 분봉 수집(전 종목 + 코어 ETF, 키움 초당 1회 ≈ 55분, 연속 20회 실패 시 중단)
   → parquet → Release 업로드(기존 자산보다 5%+ 작으면 결손 의심으로 거부)
4. **일봉 파생** — 3)의 분봉에서 정규장 봉만 골라 `daily_prices`에 upsert
5. 키움 잔고 동기화 + 계좌 스냅샷(기준일 실행에서만) + ai_decisions 채점

GitHub schedule 실행이 매 평일 밤 한 번 더 돈다(16:30 실행이 실패한 날엔 이게 재시도다).
같은 분봉 창에서 파생하므로 두 번 돌아도 일봉 값은 같다. 장이 끝나기 전에 시작한 실행은
일봉·스냅샷·체결 확정을 쓰지 않고 실패로 끝난다.

### 일봉 = 분봉의 정규장 파생 (2026-10~)

| 항목 | 정의 |
|---|---|
| 창 | 분봉 `09:00`~`15:40` (`daily.SESSION`) |
| 시가·고가·저가 | 창의 첫 봉 시가, 최대, 최소 |
| **종가** | **창의 마지막 봉 종가 = 정규장 종가.** 키움 평가(추정예탁자산)와 같은 값 |
| 거래량 | 창 안의 합계(정규장분만). 공식 거래량의 약 0.97배 |
| 행이 없는 경우 | 그날 정규장 봉이 없는 종목(거래정지 등), 분봉을 안 받은 실행(`--skip-minute`, `--tickers` 스모크, 장중 실행) |

15:30이 아니라 15:40에서 자르는 이유: 종가가 15:32·15:35 봉에서 정해지는 종목이 하루 3~12개
있다. 이 창의 파생값은 금융위 확정 시세와 전 종목 시·고·저·종이 일치한다(9/30 2,571종목).

**왜 바꿨나.** 예전엔 pykrx → FDR 상장목록 스냅샷 → 분봉 파생 순이었다. pykrx가 죽은 뒤로는
"수집 시각의 캐시 스냅샷"이 그대로 종가로 들어갔다 — 16:30 수집은 정오 무렵 값, 밤 수집은
17~20시 시간외 값. 2026-09-14부터 분봉에 16:00~19:59 봉이 생겼고 네이버 일봉
(`fdr.DataReader`)도 20:00 가격을 종가로 준다. **개별 종목의 정규장 종가를 대조할 때 네이버
일봉을 기준으로 쓰면 안 된다**(금융위 확정 시세 `kstockdata.py`나 분봉 창을 쓴다).
코어 ETF(069500) 일봉만은 `fdr.DataReader`로 받는다 — 41일 전부 정규장 종가와 같았다.

과거분 복구는 `backfill_daily.py`(같은 파생 함수, `--dates`로 날짜 지정, ETF 제외)로 한다.
`daily.py --date <과거일>`은 스냅샷과 키움 동기화를 하지 않는다 — 스냅샷은 "지금"의 키움
총자산을 그 날짜에 적으므로 과거일에 돌리면 자산 곡선이 덮인다.

### 채점 (`update_ai_returns`)

- n거래일 뒤는 시장 달력(005930의 일봉 날짜)으로 센다. 목표일에 그 종목 종가가 없으면 쓰지 않는다.
- 값이 비었을 때만이 아니라 계산값이 저장값과 다르면 다시 쓴다(60일 값이 찰 때까지).
  일봉을 고치면 다음 수집에서 채점도 따라 고쳐진다.
- `ret_basis`: `decision`(장중 판단, 측정에 쓰는 유일한 라벨) / `close`(기준가 없는 옛 계산) /
  `postclose` / `holiday` / `junk`(유니버스 결함으로 판단된 엉뚱한 종목 — 채점하지 않는다).

### 운영 주의

- **키움 IP 화이트리스트**: 키움은 계정당 IP 10개까지만 등록되며 "허용된 IP에서만
  API 인증 가능"이라고 명시한다. GitHub Actions 호스티드 러너는 IP가 유동이라
  원칙적으로 등록이 불가능하다. 만약 Actions에서 토큰 발급이 막히면
  `make_provider`가 예외를 던지므로 **잡이 즉시 실패한다** — 조용히 넘어가지 않는다.
  그때는 Actions만 `PROVIDER=naver`로 돌리고(당일 수집은 네이버로 충분),
  과거 백필은 등록된 IP(로컬)에서 키움으로 수행하면 된다.
- **cron 60일 자동 비활성화**: 저장소에 60일간 커밋이 없으면 GitHub가
  스케줄 워크플로를 끈다. 분봉은 소급 수집이 불가하므로(제공창 ~6거래일)
  장기 방치 시 데이터가 끊긴다 — 주간 백업 워크플로가 매주 커밋을 남기므로
  실질적으로 방지되지만, 백업이 실패하면 이 안전장치도 사라진다.
- 잡 실패 시 GitHub가 저장소 소유자에게 메일을 보낸다(기본 알림). 실패를
  놓치면 그날 분봉은 6거래일 뒤 영구 유실 — `workflow_dispatch`로 날짜를
  지정해 재실행할 수 있는 것도 그 창 안에서만 의미가 있다.

## 프로바이더 선택

`collector/providers/make_provider()`가 결정한다:
- `KIWOOM_APP_KEY`/`SECRET`이 있으면 **키움**(기본)
- 없으면 **네이버**로 폴백(경고 로그). 이 경우 과거 백필은 불가
- `--provider` 인자나 `PROVIDER` env로 강제 지정 가능

```sh
uv run --env-file ../.env python backfill.py --tickers 005930 --since 2026-06-01
uv run --env-file ../.env python daily.py --date 2026-07-31
```

전 종목 일일 수집 소요: 네이버 약 23분(0.5초 간격) / 키움 약 51분(1.1초 간격).
둘 다 Actions 잡 한도(6시간) 안이다.
